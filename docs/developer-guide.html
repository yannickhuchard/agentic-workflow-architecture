Specification 1.1 · SDK 2.0.0

Developer guide

The parts of the SDK you will use, each with the smallest example that works. Every example is TypeScript; the engine parts exist in Python under the same names in snake case.

Run a workflow

import fs from 'fs';
import { WorkflowEngine, parse_document, FileJournalStore } from 'agentic-workflow-architecture';

const workflow = parse_document(JSON.parse(fs.readFileSync('workflow.awa.json', 'utf-8')));
const engine = new WorkflowEngine(workflow, { journal: new FileJournalStore('journals') });

await engine.start({ claim_id: 'CLM-1' });
const status = await engine.run();     // completed | failed | waiting_human | waiting_event

A run with a failed token is failed, never completed. A choice with no true condition and no default edge fails with NO_ROUTE: the engine does not guess.

Say what must be true of a result

An outcome contract belongs to an activity. It is checked after every attempt, deterministically, and a result that breaks it is refused.

{ "name": "Assess damage", "actor_type": "ai_agent",
  "outcome_contract": {
    "output_schema": { "type": "object", "required": ["estimated_cost"], "properties": { "estimated_cost": { "type": "number" } } },
    "postconditions": [{ "name": "Within authority", "expression": "estimated_cost <= 50000" }],
    "budgets": { "max_tokens": 6000, "max_tool_calls": 4 },
    "on_violation": "escalate_human" },
  "retry": { "max_attempts": 3 } }

Read what happened

Every run writes a journal: one JSON object per line, numbered from 1 without gaps. Three levels: what happened (execution), the actor's own account of its approach (reasoning), and the engine's decisions, such as which model it chose (meta).

for (const event of await engine.getEvents()) console.log(event.seq, event.type, event.node_name);
engine.onEvent(event => { /* live */ });

Wait for the outside world

A message event holds a token until a business event arrives. Give it a deadline and a path for the deadline; without that path, a timeout fails the token rather than letting the run hang or carry on as if the event had come.

{ "name": "Documents uploaded", "event_type": "message",
  "event_definition": { "name": "documents.uploaded", "correlation_key": "customer_id",
                        "timeout": "P5D", "timeout_edge_id": "<edge taken when nothing arrives>" } }
await engine.deliverEvent(business_event('documents.uploaded', { customer_id: 'c-1' }));
await engine.expireEvents();           // deadlines that have passed take effect

Journeys that outlive the process

A journey is the life of one subject across several workflows. AwaRuntime hosts journeys and their runs behind one entry point for events, and keeps its state so that another process can carry on.

import { open_runtime_directory, business_event } from 'agentic-workflow-architecture';

const runtime = await open_runtime_directory('.awa');        // definitions, state and journals side by side
await runtime.publish(business_event('claim.submitted', { customer_id: 'c-1' }));
await runtime.tick();                                         // let deadlines pass; call on a schedule
const everything = await runtime.export_portfolio();          // what the journey view loads

The same from the command line, each command a separate process:

awa journey add intake.awa.json claim.journey.json
awa journey publish claim.submitted -d '{"customer_id":"c-1"}'
awa journey tick
awa journey list --stalled
awa journey show c-1
awa journey export -o portfolio.json

A journey may also declare its touchpoints, what changes hands and how mood is estimated; see the data model. Only one process at a time may hold a runtime directory: a second is refused while the first is alive, and talks to it over HTTP instead.

Contexts and service levels

A context is something activities share beside the data that flows along edges. An activity reaches one only through a binding, and the engine upholds it: the actor is given the contexts it is bound to read and no other, and a write needs a binding that allows it and must match the context's schema.

{{
  "contexts": [{{ "id": "...", "name": "Order", "type": "data", "sync_pattern": "shared_state", "schema": {{ "type": "object", "required": ["total"] }} }}],
  "activities": [
    {{ "name": "Receive order", "context_bindings": [{{ "context_id": "...", "access_mode": "write" }}] }},
    {{ "name": "Price order",   "context_bindings": [{{ "context_id": "...", "access_mode": "read" }}] }}
  ]
}}
// In an actor: what it was given, and what it writes
const order = inputs._contexts.Order;                      // only contexts bound for reading
return {{ priced: true, _context_writes: {{ Order: {{ ...order, total: 240 }} }} }};

A required context that nothing has written fails the activity with CONTEXT_MISSING before its actor is called; a write without a binding fails with CONTEXT_ACCESS_DENIED. shared_state replaces the value, blackboard merges into it, event_sourcing and message_passing append. In a simulation, script the writes: {"Receive order": {"contexts": {"Order": {"total": 240}}}}.

A service level (sla on an activity or a workflow) is compared with the time the work takes, waits and retries included. Past target_time the engine journals sla.warning, past max_time sla.breached, once each. Work that finished late stands. With escalation_policy.breach_action: "fail", work still waited for fails with SLA_BREACH. A host checks waiting work whenever it lets time pass:

await runtime.tick();                       // event deadlines and service levels of what is waiting
await engine.checkServiceLevels();          // the same for one engine: {{ warnings, breaches, failed }}

Measures

Specification section 21 fixes what is measured of journeys, stages, workflows and activities, so that two implementations report the same numbers from the same record. A measure is a value and the number it was computed over; it has no value, rather than zero, when there is nothing to compute it from.

import { compute_measures, measures_to_openmetrics } from 'agentic-workflow-architecture';

const report = compute_measures(await runtime.export_portfolio(), { from: '2026-09-01T00:00:00Z' });
report.journeys[0].measures['journey.completion_rate'];     // { value: 0.5, n: 6 }
report.workflows[0].measures['workflow.first_pass_yield'];  // runs right first time
report.attention;                                           // who is stuck, where, since when, and whose it is
measures_to_openmetrics(report);                            // for a metrics system to scrape
awa measures                      # for people
awa measures --json               # the report
awa measures --list               # every measure with its rule
curl localhost:3000/api/v1/measures?format=openmetrics

Give a stage an owner and a stalled journey names who must act. The measures page shows the report and opens any number into the customers behind it; it follows a running server with ?live=http://localhost:3000.

Telemetry

Specification section 26 makes every run and journey visible in OpenTelemetry. A run is one trace: a span for the run, each attempt, each tool call, each model call (provider, model and token usage, in the generative AI semantic conventions), each decision and each wait; the rest of the journal becomes span events. A journey is one trace whose run spans link to the runs' traces. Trace and span ids are derived from the run id, so what is sent live and what is exported later from the journal are the same spans, whichever SDK produced them.

import { OtlpHttpExporter, WorkflowEngine } from 'agentic-workflow-architecture';

const exporter = new OtlpHttpExporter({ traces_url: 'http://localhost:4318/v1/traces' });
const engine = new WorkflowEngine(workflow, { telemetry: exporter });  // or { telemetry: { endpoint, headers, payloads } }
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 awa run claim.awa.json    # spans leave as the run proceeds
awa telemetry export claim.awa.json run.journal.jsonl --file run.otlp.json  # a recorded run, as OTLP/JSON

Telemetry never holds up or fails a run: spans are sent in the background, and a backend that is down costs dropped spans, counted and reported, which the journal can send again. Inputs, outputs and tool arguments go on spans only when the deployment opts in. Measures can be sent as OpenTelemetry gauges too.

Tools

An activity lists the tools its actor may call. Every call goes through one runner, which refuses unknown tools, invalid arguments and calls over budget, applies the deployment's permissions, and journals the call with a link to what ran.

{ "name": "get_policy", "description": "Look up a policy by number",
  "parameters": { "type": "object", "required": ["number"], "properties": { "number": { "type": "string" } } },
  "binding": { "kind": "http", "url": "https://policies.example/api/policies/{number}" } }

Command bindings do not run unless the deployment allows commands. The default is to allow none.

The engine reaches MCP servers and gRPC services itself. An mcp binding names a server the deployment declares, a program (held to the same permission as commands) or a Streamable HTTP address; a grpc binding makes one unary call, described by the deployment's .proto files or by server reflection, over TLS unless the deployment allows plaintext for the host. Connections are kept for the run and closed when it ends.

awa run workflow.awa.json --deployment deployment.json

An activity can also be performed by an agent reached over the Agent2Agent protocol (A2A 1.0): name its agent card in the role's or the activity's a2a. The engine sends the activity and its data as a message, follows the task, and holds the reply to the outcome contract like any actor's; an agent that asks for input makes the run wait for the host's answer. awa serve --a2a workflow.awa.json offers a workflow to other agents.

Change a model without guessing

Counterfactual replay runs a recorded run again with something changed, holding everything else as it was recorded: the input, what applications and people returned, tool results, events and time.

awa replay workflow.awa.json run.journal.jsonl --candidate changed.awa.json --ai recorded

It exits with status 2 on a regression, so a folder of recorded journals is a regression suite for a change of model, prompt, contract or rule. A step the baseline never performed is reported as unrecorded; nothing is invented and no real call is made.

Evaluate a candidate on recorded work

Every visit to an AI activity is a labelled example: what the agent was given, and the outcome its contract, its verification or a person accepted, or what rejected it. Build a dataset from journals and score a candidate model or workflow against it, per activity:

awa eval build runs/*.jsonl -o dataset.jsonl
awa eval run workflow.awa.json dataset.jsonl --candidate changed.awa.json --providers ollama

The tools the candidate calls answer as they did when the case was recorded. The command exits with status 2 when the candidate loses a case the recording had accepted. A host can also run a candidate in the shadow of production: each run that ends is replayed under the candidate, nothing it does reaches the outside world, and the host reports where the two part.

Evidence for regulators

An evidence report gathers, for a period and a set of workflows, what ran, which models decided what, every human decision and escalation, every contract and verification result, refusals, failures, compensations, tool calls by target, how data was journalled, and the records held. Every statement cites the journal records it rests on, and each part names the EU AI Act articles, NIST AI RMF functions and ISO/IEC 42001 clauses it can serve.

awa evidence .awa --from 2026-09-01 --to 2026-10-01 --format html -o evidence.html

It is evidence a deployer can use. It is not a certification of compliance, and it says so.

BPMN, DMN and Serverless Workflow

Specification section 27. A workflow exported to BPMN 2.0, with its decision tables in DMN 1.3, reads back as the same document: what BPMN has no element for travels in the awa: namespace. A process drawn in a BPMN modeller imports as an AWA workflow, and what AWA cannot run the same way is refused with the element and the reason.

awa export bpmn claim.awa.json                 # claim.bpmn, and claim.dmn for its decision tables
awa import bpmn process.bpmn --dmn rules.dmn   # one workflow per process
awa export serverless-workflow claim.awa.json  # and the list of what does not map
import { export_bpmn, import_bpmn } from 'agentic-workflow-architecture';

const { bpmn, dmn } = await export_bpmn([workflow]);
const { documents, warnings } = await import_bpmn(bpmn, { dmn: dmn ? [dmn] : [] });

Mark an AI agent's task with awa:actorType="ai_agent". The TypeScript SDK reads and writes with bpmn-moddle, dmn-moddle and @serverlessworkflow/sdk, which you install beside it; the Python SDK needs nothing more. How AWA compares with BPMN, DMN, Serverless Workflow, Arazzo and agent frameworks is in docs/interchange.md.
