For architects

How AWA is put together, what it guarantees, and what it leaves to you.

Engine and host

An engine runs one workflow run. It never opens a connection to a broker and never watches the clock: it is told when an event has arrived and when a deadline has passed. A host runs engines, receives business events from wherever they come, hands them to the runs that wait, and moves journeys. A run that waits two weeks costs nothing while it waits.

This separation is deliberate. It is what lets the same engine sit behind a command line, an HTTP server or a scheduled job, and it is the seam along which the engine could be reimplemented in another language without touching hosts.

What survives a restart

StateKept as
A runA checkpoint after every step, from which another process continues under the same run id
A run's journalAppend-only, one file per run, numbered without gaps across restarts
JourneysEvery instance with its record
Events already acceptedTheir ids, so that redelivery has no further effect
Events runs have publishedAn outbox, accepted as soon as the publishing run settles

Activities are executed at least once: a run that stopped in the middle of an activity performs it again. Each attempt carries an idempotency key so that an activity with effects can be made safe to repeat.

The reference host keeps all this in one of two stores. A runtime directory of files belongs to one host at a time: a second is refused while the first is alive. A PostgreSQL store is shared: any number of hosts, in any number of processes and machines, open it and take any work (section 29).

On a shared store each operation of a host (taking in an event, letting time pass, completing a task) is one transaction. It holds the partitions it touches, one per subject and one per run outside a journey, and others wait for them; work on different subjects goes on at once. An event's id is recorded in the same transaction, under a primary key, so no event is taken twice; rows are written back at the version read; a host that dies releases what it held when its connection drops, and one that hangs when its lease runs out, with nothing of its operation kept. The outcome is that of one host doing everything one operation at a time, and the TypeScript and Python SDKs share one store.

awa journey add claim.awa.json claim.journey.json --store postgres://awa@db/awa
AWA_RUNTIME_STORE=postgres://awa@db/awa awa serve --port 3000   # on as many machines as you like

Install the optional database client first: npm install pg, or pip install "agentic-workflow-architecture[postgres]".

What may run

A workflow document can name any URL, program or agent. What actually runs is the deployment's decision: command bindings need explicit permission, and so do MCP servers the engine would start; HTTP, JSON-RPC, MCP and gRPC bindings and A2A agents can be restricted to listed hosts; an MCP binding reaches only a server the deployment declares; and secrets are substituted at call time and never journalled. The link to what ran is always journalled, even when payloads are hashed or omitted. In simulation nothing is called.

Who may do what is the deployment's decision too (section 30). Its authorization section names the principals of agents and applications, and a policy of rules (subject, action, resource, condition) that allow or deny. People come from the authenticated request. Under a policy, what no rule allows is denied and a denial wins; separation of duties (who submitted may not approve) and four-eyes approvals are rules of their own. The engine asks before a run starts, before an agent performs an activity or reaches an agent over A2A, before a tool call and when a person completes a task; a refusal fails with FORBIDDEN and is journalled as authorization.decided, and every completion names who performed it. An external policy engine can be plugged in as the decider.

What AWA does not do

  • Access rights to external resources are declared, not enforced. The document states them and they can be queried. Context bindings (section 22) and service levels (section 23) are enforced; the permissions of tools are the deployment's (section 17.4).
  • No streaming calls. gRPC tools make unary calls; an agent offered over A2A answers requests, without streaming or push notifications.
  • No broker. Events enter and leave through the host. Connecting Kafka, a queue or a webhook is the host's job.
  • One subject at a time. Hosts on a shared store share the work across subjects; the operations on one subject run one after another. Activities still run at least once, and the database's own replication is yours.
  • Model providers have not all been exercised against live services in the reference tests; they are tested against stubs.
