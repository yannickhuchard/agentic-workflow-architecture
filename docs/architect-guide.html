For architects

How AWA is put together, what it guarantees, and what it leaves to you.

Engine and host

An engine runs one workflow run. It never opens a connection to a broker and never watches the clock: it is told when an event has arrived and when a deadline has passed. A host runs engines, receives business events from wherever they come, hands them to the runs that wait, and moves journeys. A run that waits two weeks costs nothing while it waits.

This separation is deliberate. It is what lets the same engine sit behind a command line, an HTTP server or a scheduled job, and it is the seam along which the engine could be reimplemented in another language without touching hosts.

What survives a restart

StateKept as
A runA checkpoint after every step, from which another process continues under the same run id
A run's journalAppend-only, one file per run, numbered without gaps across restarts
JourneysEvery instance with its record
Events already acceptedTheir ids, so that redelivery has no further effect
Events runs have publishedAn outbox, accepted as soon as the publishing run settles

Activities are executed at least once: a run that stopped in the middle of an activity performs it again. Each attempt carries an idempotency key so that an activity with effects can be made safe to repeat.

The reference host keeps all this in a directory of files, which one host holds at a time: a second is refused while the first is alive. Several hosts sharing one store need coordination the reference host does not do; the PostgreSQL DDL shows the shape a shared store would have.

Each level has language-neutral cases in spec/conformance; both SDKs run every case of every level, none skipped. What the cases cannot reach (live model providers, Open Knowledge Format exchange, the recipe) is fixed by each SDK's own tests.

What may run

A workflow document can name any URL or program. What actually runs is the deployment's decision: command bindings need explicit permission, HTTP and JSON-RPC bindings can be restricted to listed hosts, and secrets are substituted at call time and never journalled. The link to what ran is always journalled, even when payloads are hashed or omitted.

What AWA does not do

  • Access rights to external resources are declared, not enforced. The document states them and they can be queried. Context bindings (section 22) and service levels (section 23) are enforced; the permissions of tools are the deployment's (section 17.4).
  • No built-in MCP or gRPC executor. The bindings are specified; a deployment supplies the executor.
  • No broker. Events enter and leave through the host. Connecting Kafka, a queue or a webhook is the host's job.
  • No multi-host coordination. See durability above.
  • Model providers have not all been exercised against live services in the reference tests; they are tested against stubs.

The normative text is the specification. Where this guide and the specification disagree, the specification is right.
