| 2026-11-23 | 22:00 | **Changing a workflow while runs are in flight** (specification section 25, conformance level `versioning`). **Versions**: a host keeps every registered version of a workflow; a run stays on the version it started on, after a restart and on a shared store too; new runs, and those journeys and events start, take the newest, unless the caller names a version or the host pins one (`pinned_versions`). A runtime directory keeps each version in `definitions/workflow-<id>@<version>.json`; the PostgreSQL store keeps each as a row (store migration 2: the key of `awa_runtime.definitions` becomes kind, id and version). A host refuses to start where a run needs a version it has not registered. **Migration**: a plan (`to_version`, `nodes` old id to new id with the identity mapping for the rest, `restart`, `data` assignments of a value, a copied path or a condition expression's result, each with an optional `when`) moves a run at rest (waiting for a person, an event, an agent, a timer or a join) to another version. It is checked whole first and refused, changing nothing, with every reason named (`run_in_activity`, `unmapped_token`, `wait_incompatible`, `invalid_assignment` and eight more); a dry run reports what would happen. Applied, it is one change recorded as `run.migrated`. **Compatibility**: `compare_versions` and `check_migration` classify each position at rest of an older version as `compatible`, `needs_mapping` (with candidate nodes) or `impossible`, and each live run as migratable or not. Replay matches a migrated run as its migrations mapped it; evidence states each migration; telemetry ends the spans of a withdrawn wait; measures count the run once. New command `awa migrate check\|plan\|apply` (`--dir` or `--store`; exit status 2 on refusal) and routes `GET /api/v1/journeys/workflows/{id}/versions`, `POST /api/v1/journeys/migrations/check`, `POST /api/v1/journeys/runs/{run_id}/migrate`. Both SDKs pass the 12 new cases. **Changed behaviour**: registering an older version of a workflow after a newer one no longer makes it the one new runs start on; `awa journey add` writes workflow files named by id and version. | No |
| 2026-11-23 | 16:00 | **Evidence, evaluation from journals, and shadow runs** (specification sections 32 and 33, conformance levels `evidence` and `evaluation`). **Evidence**: `compute_evidence` and `awa evidence <dir-or-journals...> [--from --to] [--workflow] [--format json\|md\|html]`, and `GET /api/v1/evidence`, compute from journals and journey records what ran, which models decided what, every human decision, override and escalation, every contract and verification result, refusals, failures, compensations, service level breaches, tool calls by target, data by payload mode and the records held. Every statement cites the records it rests on (run id and `seq`), and each part names the EU AI Act articles (12, 13, 14, 15, 26), NIST AI RMF functions and ISO/IEC 42001 clauses it can serve; the report says it is evidence a deployer can use, not a certification. Schema `spec/json-schema/evidence-report.schema.json`. **Evaluation**: `awa eval build` turns each visit to an AI activity into a case (its input; the outcome accepted by contract, verification or a person, or what rejected it), and `awa eval run` performs every case again under a candidate through counterfactual replay and reports pass rates against contracts and verification per activity, with regressions and improvements; exit status 2 on a regression. Schemas `evaluation-case` and `evaluation-report`. **Shadow runs**: the host option `shadow` replays each production run that ends under a candidate; tools, people and other actors never run, and `runtime.shadow.report()` gives the measures of both and the runs where they part. Both SDKs, 8 new conformance cases | No |
| 2026-11-23 | 18:00 | **MCP and gRPC executors; agents over A2A**. **Tools** (specification 17.7, 17.8): the engine now runs `mcp` bindings itself, over standard input and output (a server the deployment declares as a program, started only when `allow_commands` allows it) or Streamable HTTP (held to `allowed_hosts`), with the initialize handshake of MCP 2025-11-25; and unary `grpc` calls, described by the deployment's `.proto` files or by server reflection, over TLS unless the deployment allows plaintext for the host, the tool's timeout as deadline, status codes mapped to `tool.failed`. Connections are kept for a run and closed when it ends or waits. A deployment declares its servers in a deployment file (`awa run --deployment`, `awa serve --deployment`: `tools.mcp_servers`, `tools.grpc`, `a2a`). gRPC needs `@grpc/grpc-js` and `@grpc/proto-loader` (optional) in TypeScript and the `grpc` extra in Python. **Agents over A2A** (section 28, A2A 1.0, JSON-RPC binding, as `@a2a-js/sdk` 1.x and `a2a-sdk` 1.x implement it): a role or an activity names an agent card in `a2a`; the agent performs the activity under the same outcome contract, verification, retry policy, permissions and record (`agent.message_sent`, `agent.task_updated`); a task that asks for input makes the token wait (`waiting_human`) until the host answers with `answerAgent` / `answer_agent`; nothing is called in simulation. `awa serve --a2a <file>` offers a workflow as an A2A agent with its card at `/.well-known/agent-card.json`. New conformance level `a2a` (15 cases), passed by both SDKs; each SDK's A2A client is tested against the other SDK's host and against the reference A2A SDKs. **Breaking**: an `mcp` binding that names a server the deployment does not declare, run by the built-in executor, is now refused with `PERMISSION_DENIED` (it failed with `VALIDATION_ERROR` for want of an executor); a registered executor still replaces the built-in one. | Yes |

| 2026-11-23 | 20:00 | **Hosts that share a store** (specification section 29, conformance level `shared_store`). Several hosts, in several processes or on several machines, keep journeys and runs in one PostgreSQL database and take any work, with the outcome of one host doing everything one operation at a time. A store contract that any store can meet: partitions (one per subject, one per run outside a journey), each operation one unit that holds the partitions it touches, an event id accepted once, deadlines found and taken by whichever host is free, waits and the events that may reach them ordered, a host that dies or hangs releasing what it held with nothing of its operation kept, versions checked on every write. The runtime directory meets it for one host; the new **PostgreSQL store** for many: advisory locks per partition, the primary key of `business_events`, writes checked against the version read, a lease as the idle transaction timeout, tables created by migrations (section "Runtime store" of `spec/ddl/awa.postgresql.sql`, schema `awa_runtime`). **TypeScript**: `PostgresRuntimeStore`, `open_runtime_store`, `AwaRuntime({ shared })`, `runtime.refresh()`; optional package `pg`. **Python**: the same, with the extra `postgres` (psycopg 3); the two SDKs keep the same forms and share one store. `awa journey` and `awa serve` take `--store <url>` or `AWA_RUNTIME_STORE` (not `AWA_DATABASE_URL`, the task database). 8 conformance cases played by several hosts, passed by both SDKs; tests of bursts across 6 host objects and 4 processes (0 events applied twice), a process killed mid-operation, a lease that runs out, an event racing a new wait, and TypeScript and Python hosts on one store. CI job with a `postgres:16` service. A run taken up by another host records no `run.resumed`. | No |
