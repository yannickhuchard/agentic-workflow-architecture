# AWA visualisation tools

| File | What it shows |
|---|---|
| `replay.html` | One run, replayed from its execution journal: animated tokens, node states, a timeline you can scrub, and the reasoning behind each step |
| `journey.html` | Several journeys and the customers in them: an atlas, one journey on calendar time, one customer's journey as a blueprint with mood, touchpoints, technology and what changed hands, and the run behind any part of it |
| `dashboard.html` | The measures of journeys and workflows (specification section 21): who is stuck and whose it is, what became of the journeys, how the work went, where the time and the money go, with every number opening the customers behind it |
| `index.html` | A workflow definition, in 2D or 3D |
| `live.html` | A running workflow, by polling a local demo server |
| `awa-brand.js` | Reads a company's brand (a DESIGN.md or a brand.json) and puts it on the journey view, the replay and the measures page ([Branding](#branding)) |
| `awa-glossary.js` | The terms the journey view's glossary explains ([Glossary](#glossary)) |
| `awa-recommendations.js` | The recommendations of a record: twelve rules over the measures and the journal, and the journey's own ([Recommendations](#recommendations)) |
| `recommendation-replay.mjs` | Measures the effect of a recommendation by counterfactual replay, where a replay can, and stores the reports with the example |
| `awa-dossier.js`, `awa-dossier-html.js`, `awa-dossier-print.js`, `awa-dossier-docx.js`, `awa-dossier-node.js` | The dossier of a journey: its content, and its HTML, PDF (print layout) and DOCX writers ([tools/dossier](../dossier/README.md)) |
| `brands/` | AWA's own design tokens (`awa.DESIGN.md`) and a fictional company's brand to start from (Valoria Life, light and dark) |

## Replay

`replay.html` is a single file with no dependencies. Open it in a browser and either pick a sample run or drop two files on the page: the workflow definition (`.awa.json`) and the journal of one of its runs (`.journal.jsonl`).

To produce a journal:

```bash
awa run workflow.awa.json --journal run.journal.jsonl
```

It also loads from URLs, and can follow a run live from an AWA server over Server-Sent Events:

```
replay.html?workflow=<url>&journal=<url>
replay.html?run=http://localhost:3000/api/v1/workflows/runs/<run id>
```

| Control | Action |
|---|---|
| Space | Play or pause |
| ← → | Step back or forward one journal event |
| Home, End | Go to the start or the end |
| Click a node | See its contract, its attempts and what happened there |
| Drag, scroll, double-click | Pan, zoom, fit |

The picture at any position is computed from the journal events up to that position and nothing else, so what you see is exactly what was recorded. Marks above the timeline show failures (red), tool calls (green), actor reasoning (blue) and engine decisions (amber). A tool call's step shows what it ran, as a link, with its arguments, result, status and time.

`replay-sample.js` holds the sample runs. It is generated by `examples/claims-settlement/make-runs.mjs`.

## Measures

`dashboard.html` needs no build step and no network. Open it in a browser: it shows the sample (`dashboard-sample.js`, the same six customers as the journey view).

| How | What |
|---|---|
| "Open a record" | The file written by `awa journey export` |
| `dashboard.html?data=<url>` | The same, from an address |
| `dashboard.html?live=http://localhost:3000` | A running AWA server, read every few seconds |
| `&options=<url>`, with `?data=` or `?live=` | The journey view's options (below): the page names customers by `subject_name`, and passes the options on to the journey view |
| `window.AWA_dashboard_show(record, source)` | For a page that embeds this one. It may set `window.AWA_open_journey = (journey, instance, record) => …` to say how a customer's journey is opened when no journey view sits beside the page |
| `awa measures --html measures.html` | One file with the record inside it: nothing to install, nothing fetched, to send to someone or attach to a report |
| `http://localhost:3000/views/dashboard.html?live=http://localhost:3000` | The page as `awa serve` serves it: the SDK package carries the measures page and the journey view |

The page reads top to bottom as four questions: who needs someone now; do customers get what they came for; does the work go right; how did it go over time. A journey opens into its stages, a workflow into its steps, tools, errors, waits and decisions.

What it holds to, from `docs/ux/dashboard-research.md`:

- Every rate comes with its count, and below ten the count leads: "3 of 6", then "50%".
- A measure with nothing behind it reads "no value", never 0.
- What became of customers (the journey's goal) and whether runs completed (the machinery) are separate sections. A run can complete and the customer still be lost.
- Mood is a spread of dots, solid when the customer said it and dashed when a rule inferred it, with the share that was said.
- Any number opens the customers or runs it counts, with the rule of the measure, and each of them opens in the journey view.

The numbers are computed in the page by `awa-kpis.js`, which is built from the SDK (`npm run build:measures` in `sdk/typescript`), so the page, `awa measures` and `GET /api/v1/measures` cannot disagree. `dashboard.check.mjs` checks the page in a browser against the measures computed outside it (needs Playwright).

## Journeys

`journey.html` needs no build step and no network. Open it in a browser: it shows the sample (`journey-story.js`, six customers through three journeys).

To see your own journeys:

| How | What |
|---|---|
| "Open a record", or drop a file on the page | The file written by `awa journey export`, or by `GET /api/v1/journeys/portfolio` |
| `journey.html?data=<url>` | The same, from an address |
| `journey.html?live=http://localhost:3000` | Follows an AWA server: the view updates as journeys progress, and a reader at the latest moment stays there. `&poll=<ms>` reads it that often (3000 by default, 500 at least) |
| `&options=<url>`, with `?data=` or `?live=` | The builder's options for this record, as JSON (below) |

`journey-story-builder.js` turns a record into what the view plays. It works on any record; an example may pass it options, as `examples/claims-journey/make-story.mjs` does and as `?options=` does for a record the view loads:

| Option | Meaning |
|---|---|
| `layouts` | By workflow name, `{ "<node name>": [column, row] }`: a layout made by hand. It replaces the rule when it places every node of the workflow |
| `bands` | By workflow name, `[{ "row": 0, "label": "…" }, …]`: the rows where each band of a long workflow starts. Each band is a row of columns of its own, and the run view shows one band at a time |
| `subject_name` | Paths in a journey instance's data whose values, joined by a space, name its customer: `["applicant.first_name", "applicant.last_name"]`. The record's `subject_name` comes first; without either, the customer is named by the journey's key |
| `sentences` | By event type, `(name, data) => [title, sentence]`: how a business event is told. A function, so only for a page or a script that calls the builder |
| `glossary` | The journey's own words, shown in the glossary under "This journey": `[{ "id"?, "term", "definition", "see"?, "aliases"? }]`. `see` is an https address, shown as a link, or a short text such as "Example"; `aliases` are other words a search finds the term by. The view reads the options, not the builder |

`examples/electricity-onboarding/views/story-options.json` is a complete example: names, a 43-node layout in three bands, and a layout of its child workflow. The measures page takes the same `?options=` to name customers, and passes it on to the journey view it links to.

In a layout with bands, an edge to a node in another band leaves by the clear lane beside its source's column, runs along the gap next to the target's band, and comes into the target; a band beyond the next one is reached round the left edge of the bands. An edge back to an earlier column of the same row goes over a track above the row. A small note says where an edge comes from or goes to, "from band 1", "to band 3, Generate contract". Layouts without bands are routed as before.

Every activity box of a workflow has the same size: 140 × 72, which holds a tag and a name of three lines at 12 px. When a name of the workflow needs a fourth line, the builder widens every activity box of that workflow together, to 164, then 188, by 24 at a time up to 260, until each name fits in three lines. The builder measures names without a browser, since it also runs in Node (the checks, the MCP server): a table of character widths at 12 px semibold, the wider of Inter and Arial for each character, plus 5 %, so that a name it measures at three lines never wraps to a fourth on screen. A name longer still is cut after three lines with an ellipsis, and the box's tooltip gives it whole.

The run view draws names at 11 px or more on the 1440 × 900 stage: it scales a band, or a workflow without bands, to fill the graph's area, at 11/12 of its size at the least. A graph wider than that shows the part around the step being read, follows the steps as they move, and offers an arrow at each edge where there is more to see; a horizontal scroll (or Shift and the wheel) moves it too. The next step brings the step being read back to the centre.

`journey.check.mjs` checks the view in a browser (needs Playwright), the options included. In the run views it opens (every workflow of the sample, each band of the electricity example and its child workflow) it checks that every name stays inside its box, that no node lies on another, and that names are drawn at 11 px or more.

| Height | Shows | Go down by | 
|---|---|---|
| Journeys | Each journey with its stages and outcomes, how many customers go on to the next, and each customer's path and mood across them | Selecting a journey, or a customer's cell |
| One journey | Every customer in it on calendar time, with live counts per stage | Selecting a lane |
| One customer's journey | Mood, touchpoints, the journey's stages, the workflows behind them, the technology used and the documents exchanged, against the same moments. On a long journey, a stage too narrow for its name shows a short form, with the full name on hover and focus and as its accessible name; where the labels of the time between moments would cover one another, the longest gaps keep theirs and every gap stays drawn | Selecting a workflow bar |
| One run | The workflow replayed step by step, with the journal evidence for each step, under the stage the journey instance records for the run. A workflow in bands shows a chip per band, numbered and marked done, now or next; the graph shows the band of the step being read, large enough to read, and slides to the next band when the step moves there. A chip shows another band | |

The switch at the top right moves sideways to another journey; on one customer's journey it keeps the customer. The arrows beside a customer's name move to the next customer in the same journey.

| Control | Action |
|---|---|
| Play, or the buttons beside it | Tell the story, step, or return to the start |
| ← → | Step back or forward |
| Esc | Go up one height |
| The address | Carries the place, `#level/journey/customer/run/position` (`#story/0/2/0/999` is the third customer's latest moment): copy it to share exactly what you are looking at. A page that embeds the view, or a link, may change it while the page is open, and the view goes there |
| Glossary, or ? | Opens the glossary beside the view; ? or Esc closes it, and the focus returns to where it was |

### Glossary

The Glossary button in the top bar (or the ? key) opens a panel beside the view. It lists the words of the view and of AWA, each in one plain sentence with where it comes from: the section of the specification for AWA's terms (§19.2 for a stage), "View" for a word of the view itself, and for a journey's own terms the short text or the https link its options give. A search ("Search 60 terms") filters as you type, by the term, its other names and its sentence; chips show one group: This journey, Journeys, Work, Trust, Measures. While the panel is open, Tab stays inside it; Esc or the close button closes it.

Words of the view are dotted, and selecting one opens its entry: the legend of the run view ("working now", "waiting", "done", "failed", "undone afterwards", "path taken on a missed deadline"), the legend and the row names of the blueprint, the actor tags on activity boxes (AI agent, Person, System, Robot, Undo step), the run's status, "stalled" and "left" on the stage cards, "Bands", and "Journal record" in the evidence.

The address opens it too: `#glossary` or `#glossary/<term id>`, alone or after the place, as in `#run/1/1/1/3/glossary/four-eyes`. The view writes the panel into the address while it is open, so a copied address opens the same entry.

AWA's terms are in `awa-glossary.js` (`window.AWA_GLOSSARY` in a page, `require()` in Node): 60 terms, each citing a section or, for a word of the view, "View" checked against `docs/specification.md`. A journey adds its own through the `glossary` option; `examples/electricity-onboarding/views/story-options.json` adds eight (metering point, EAN code, prosumer, export tariff, grid export registration, supplier switch, direct debit mandate, commissioning report). Option text is shown as text, never as markup, and `see` becomes a link only when it is an https address.

On one customer's journey nothing is hidden: selecting a mark reads that moment and dims what comes after. "Read as a list" gives the same story as a dated list, by default only the customer's side.

A filled dot and a solid stretch of the mood line are something the customer said. A hollow dot and a dashed stretch are an inference by a rule of the journey; the caption gives the rule's reason.

## Recommendations

**Recommendations**, beside the heights in the bar, with its count, opens the tab of what to change (design boards 12 to 12d). `#recommendations` opens it, `#recommendations/<id>` opens one recommendation; every other address works as before.

| Part | What it shows |
|---|---|
| The map | Impact against effort, one mark per recommendation: its size is the customers concerned, its shape and colour the kind (speed circle, quality square, cost diamond, trust hexagon, experience ring), a number beside it, so colour is never the only cue. The marks settle on a spring when the tab opens. "Do first" is high impact for low or medium effort |
| The cards | The same recommendations ranked by impact over effort: the rule and numbers that fired it, the customers, how the effect is known (Replay, Estimate, Pilot, Replay not run), and what this viewer decided |
| Filters | Journey, stage and kind. A stage with none shows the empty state: the seven checks it passed, with what each found and its threshold |
| The panel | Why it fired (each rule with its numbers and threshold), the customers behind it with **Blueprint ›**, which opens their journey, and a link to the run at the step or the journey record the rule points at, the expected effect and how it is known, the action, and Accept, Dismiss with a reason, Add to the dossier, kept in this browser for this viewer |
| Before and after | For a recommendation measured by replay: the run as recorded and with the change, the boxes moving to their place, and the replay report (specification section 20.3) with its effect on the measures. **T** toggles |

| Control | Action |
|---|---|
| ← → ↑ ↓ on the map | Move to the nearest mark that way |
| Home, End | The first and the last by rank |
| Enter or Space | Open the recommendation |
| Escape | Close the panel (or the before and after) and give the focus back to the mark or card that opened it |
| T | Before and after |

Under `prefers-reduced-motion` nothing moves: the marks are in place at once and the panel does not slide.

`awa-recommendations.js` computes them, in the page and in Node (`require`), from the record the view shows; the MCP server computes them beside the story it sends the journeys widget. No DOM, no clock: the same record and options give the same recommendations. The twelve rules:

| Rule | Fires when | Default threshold |
|---|---|---|
| R1 | A stage outlasts its time: its share of entries that stalled (`stage.breach_rate`) | > 10%, at least 5 entries |
| R2 | The outcome contract hands a run over to a person at an activity | ≥ 10% of runs |
| R3 | The same guardrail blocks the same input again in one run | ≥ 2 |
| R4 | The policy refuses a person at a task (`authorization.decided` deny) | ≥ 1 |
| R5 | Customers need a reminder (a touchpoint whose id or name says remind) | ≥ 10% of journeys |
| R6 | Mood falls at a stage | a change of −0.5 or lower |
| R7 | One activity holds most model tokens | > 50% |
| R8 | Customers leave at a stage | ≥ 10% |
| R9 | Right first time is low (`workflow.first_pass_yield`) | < 80% |
| R10 | The customer hears nothing: the longest time between touchpoints with them | ≥ 7 days |
| R11 | An awaited event never comes (`event.timed_out`) | ≥ 1 |
| R12 | A service level slips: runs with a warning or a breach | ≥ 25% of runs |

What the rules find is joined into actions: a silence into a touchpoint, handovers into a smaller attempt budget, refusals into routing, a wait that runs out into a shorter wait or a follow-up, reminders into an earlier reminder, a costly activity into a lighter model for the clear cases. Each recommendation has its owner (the stage's `owner`), the customers concerned with their run and journal record, impact = customers concerned ÷ journeys started × severity (3 a journey lost or a run failed, 2 a stage or a promise outlasted or a fall of mood, 1 friction, 0.25 a cost below materiality), effort (1 options, policy or a contract budget; 2 a workflow change; 3 new work for people), priority = impact ÷ effort, and how its effect is known: measured, replay, replay not run, estimate or pilot.

The options' `recommendations` (all optional):

| Option | Meaning |
|---|---|
| `thresholds` | `{ "R1": 0.05, "R10": "P5D" }`: a number sets a rule's main threshold, an object (`{ "R1": { "share": 0.05, "min_entries": 3 } }`) any of them |
| `materiality` | `{ "cost_per_journey": 1.0 }`: below it, cost weighs 0.25 |
| `reminders` | The touchpoint ids that are reminders |
| `wording` | `{ "<id>": { "title", "action", "finding", "effect" } }`: the journey's own words for a recommendation the rules make |
| `rules` | Domain recommendations: `{ "id", "title", "kind", "stage", "owner", "effort", "for": "customer" or "journey", "when": <condition>, "finding", "action", "effect": { "method", "text" }, "rules": ["R8"] }`. A rule that names R8 at its stage takes the place of the generic one |
| `replays` | The replay reports, or the path of `replays.json` relative to the options file (the page reads it) |

A condition is data, never code: `{ "all": [...] }`, `{ "any": [...] }`, `{ "not": ... }`, or a test `{ "field": "data.outstanding_debt_eur", "gt": 1000 }` on a customer (`status`, `stage`, `stalled`, `days`, `mood`, `reached.<stage>`, `touchpoints.<id>`, `data.<path>`) or `{ "measure": "stage.abandoned", "stage": "invitation", "gte": 1 }` on the journey's measures, with `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in` or `exists`. A text may hold `{names}`, `{count}`, `{of}`, `{stage}`. `examples/electricity-onboarding/views/story-options.json` offers a payment plan before declining; `examples/life-insurance-savings/views/story-options.json` proposes a top-up before 31 December to a member below the Art. 111bis ceiling.

`node tools/visualization/recommendation-replay.mjs` replays, with `ai: "recorded"`, the runs behind each recommendation a replay can measure (today an outcome contract's attempt budget), and writes `examples/<name>/recommendations/replays.json` with each report in `replay/`. The replay supplies the step's recorded result, so it shows what the rest of the run does under the change (status, path, who decided, regressions); the attempts and the agent time at the step come from the recorded attempts. On the electricity example: attempts at the step 4 → 2, agent time 14 → 7 minutes, outcome contracts met 33 of 37 → 33 of 35, no regression.

**Export dossier**, in the bar, opens the export dialog: audience (client or professional), scope, sections, brand, formats, the persona the narrator picked, a preview and the accessibility check. It makes the HTML edition of the dossier in the browser, offered as a link, and gives the command for the PDF and the DOCX ([tools/dossier](../dossier/README.md)).

## Branding

A company can show the journey view, the replay and the measures page in its own colours, fonts and corner radius, with its logo and name in the header and "powered by AWA" beside them. The views read the brand from a [DESIGN.md](https://github.com/google-labs-code/design.md) file, the open format Google Labs published for describing a design system to agents (Markdown with YAML design tokens; the format is specified in [docs/spec.md](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md) of that repository, version "alpha" when this was written), or from a small `brand.json` with the same tokens.

### Step by step

1. Write or export a DESIGN.md. A design tool or an agent that writes the format gives you one; otherwise copy `brands/valoria-life.DESIGN.md` and change the values. At least `colors.primary`; usually also `colors.surface` and `colors.on-surface`, a heading and a body font under `typography`, and `rounded`. Write hex colours in quotes: in YAML, a `#` starts a comment.
2. Add your logo beside it (an SVG or a PNG), and name it in the front matter: `logo: my-logo.svg`, and `logo_dark:` for a version that reads on a dark page. These two keys are AWA's addition to the format; other tools ignore them.
3. Host the DESIGN.md and the logo next to the views, on the same server (a page opened from a file cannot fetch another file).
4. Open a view with `?brand=<address of the DESIGN.md>`: `journey.html?brand=brands/my-company.DESIGN.md`, `dashboard.html?brand=…`, `replay.html?brand=…`. The address is relative to the page. With `?options=<url>`, the options can carry it instead: `"brand": "my-company.DESIGN.md"` (relative to the options file) or a brand.json object. The measures page passes `?brand=` on to the journey view it links to.
5. Open the browser's console: the view names every token it left out or adjusted, such as `colors.primary (#ffe08a) reads at 1.4:1 on the page, under 3:1 for a mark; its lightness is adjusted`.

### What the tokens become

| DESIGN.md token | In the views |
|---|---|
| `colors.primary` | The accent: buttons, focus, the selected crumb and chip, the stage and step in view, bars on the measures page, links and words in the accent colour. A button's fill is the primary, darkened or lightened until `on-primary` reads on it at 4.5:1 |
| `colors.on-primary` | Text and icons on a button |
| `colors.surface` | The page |
| `colors.on-surface` | Text; at low opacity, the lines between things. The softer and muted words are mixed from it and the surface, at 4.5:1 or more |
| `colors.on-surface-variant` | Secondary text |
| `colors.surface-container-low` | Panels and the top bar (else a step from the surface) |
| `colors.surface-container` | Cards and the boxes of a workflow (else white in light mode, a step lighter in dark mode) |
| `colors.surface-container-high` | Hover and raised surfaces |
| `colors.outline` | The borders of a workflow's boxes |
| `colors.light.*`, `colors.dark.*` | The same tokens for one mode: the mode group is laid over the top-level tokens |
| `typography.<headline…, display…, title…, h1…>.fontFamily` | The display font: titles, the company's name, large numbers |
| `typography.<body…>.fontFamily` | The body font |
| `rounded.md`, `rounded.lg` | The radius of buttons and boxes, and of cards and panels (`lg` defaults to `md` × 1.5) |
| `name` | The company's name in the header |
| `logo`, `logo_dark` (AWA's addition) | The logo in the header, as an image |
| `{colors.primary}` | A token reference is followed to the value it names |

The mode is the brand's `mode` (brand.json), else that of its surface (dark below a relative luminance of 0.18), else, for a brand with both a `light` and a `dark` group or with no surface, the reader's preference. A token the brand leaves out comes from AWA's own tokens for that mode (`brands/awa.DESIGN.md`, which `awa-brand.js` holds as `AWA`): the views look as they always have when no brand is given.

A font is loaded from Google Fonts with a stylesheet link (`fonts.googleapis.com`, weights 400 to 700) unless the page already has it (Inter, the system fonts); a family Google Fonts does not have falls back to the view's own stack. A family name is read only when it is plain letters, digits, spaces and hyphens.

### brand.json

```json
{
  "name": "Valoria Life",
  "logo": "valoria-life.svg",
  "logo_dark": "valoria-life-dark.svg",
  "mode": "light",
  "colors": { "primary": "#0E7C66", "on-primary": "#FFFFFF", "surface": "#F6F7FB", "on-surface": "#0F172A" },
  "typography": { "heading": { "fontFamily": "Space Grotesk" }, "body": { "fontFamily": "Inter" } },
  "rounded": { "md": "8px", "lg": "12px" }
}
```

`colors`, `typography` (by DESIGN.md token, or `heading` and `body`), `rounded` and `name` are the DESIGN.md tokens; `logo` and `logo_dark` are addresses (relative to the brand.json) or `data:` images; `mode` is `dark`, `light` or `auto`.

### Contrast and meaning

- The colours of states keep their hue whatever the brand: working now (purple), waiting (amber), done (green), failed (red), undone (grey), and on the measures page stuck (amber) and left (orange). Only their lightness changes, so that each reads at 3:1 as a mark and 4.5:1 as a word on the brand's page, panels and cards (WCAG 2.2, 1.4.11 and 1.4.3).
- `on-surface` must read at 4.5:1 on `surface`, and `primary` at 3:1 on the page and the panels; the accent used for words reads at 4.5:1. Where a brand's colour fails, the view moves its lightness as little as needed and says so in the console, naming the token.
- Every colour, dimension and font is checked before it is used. A colour is read as hex (`#RGB`, `#RGBA`, `#RRGGBB`, `#RRGGBBAA`), `rgb()`/`rgba()` or `hsl()`/`hsla()`; anything else is left out with a warning, so a value can never carry CSS of its own.
- The name is shown as text. The logo is shown in an `<img>` (an SVG is never inlined), from an http or https address or a `data:` image of up to 400 kB.

### What the views do not read

The DESIGN.md format has more than the views use. They do not read `spacing`, `motion`, `components`, `omitted`, external `@` references, font sizes, weights, line heights and letter spacing (the views keep their own type scale, sized for the 1440 × 900 stage), named colours (`red`), `hwb()`, `oklch()`, `oklab()`, `lch()`, `lab()` and `color-mix()`, breakpoint groups of `typography`, or the Markdown prose. `secondary`, `tertiary`, `neutral` and `error` are accepted and not used (`neutral` stands for the surface when there is no `surface`): the views have one accent, and their red for "failed" is a state colour, not a brand colour. The YAML reader takes the subset the format uses (maps, lists, flow maps and lists, quoted and plain scalars, block scalars, comments) and refuses anchors, aliases and tags.

### Examples

| File | What it is |
|---|---|
| `brands/awa.DESIGN.md` | AWA's own tokens, dark by default with a light mode. A root `DESIGN.md` would clash with the repository's `DESIGN.MD` on a file system that ignores case, so it lives here |
| `brands/valoria-life.DESIGN.md`, `valoria-life.brand.json` | A fictional insurer: teal primary (#0E7C66) on a light page, Space Grotesk and Inter, with its logo (`valoria-life.svg`) |

Valoria Life is made up for AWA's examples; its name, logo and colours belong to no real company.

`journey.check.mjs` and `dashboard.check.mjs` check a DESIGN.md and a brand.json (accent, page, fonts, logo, name), that the light mode reads at 4.5:1 at every height of the journey view and on the measures page, that a colour that is not one is refused, that a primary too light is darkened with a warning, and that the colours of states keep their hue and pass contrast.

The MCP server's widgets take a brand inline: see `apps/mcp-server/README.md`.
